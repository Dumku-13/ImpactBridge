# ImpactBridge — Build Plan

## Context

ImpactBridge is a grant & nonprofit funding management platform ("Airbnb meets LinkedIn for nonprofits and donors") with four roles: **NGO Admin, Donor, Company/Funder, Platform Admin**. What makes it stand out from a generic donation app is the **funder → grant workflow** (a real multi-stage state machine) layered on top of a thoughtful relational schema (~15 tables) with role-based access.

**Why we're building it / goals (from the user):**
- **Portfolio / interview showcase** — depth over breadth; clean schema, thoughtful relationships, a few standout features that work flawlessly.
- **Learning the full stack** — the user knows the stack conceptually but Claude writes the code and **explains the tricky parts as they're built** (Prisma relations, auth, Stripe webhooks, Socket.io) so the user can speak to any of it in an interview.

**Hard requirement:** In a previous interview, donations did not work and disappointed the interviewer. **This time donations must genuinely work.** We use **Stripe test mode** — real Stripe API and real payment flow, paid with test cards (no real money). The full loop (Checkout → webhook → recorded donation → receipt → updated dashboard) must be demoable live. This is the centerpiece of the first slice and gets built carefully so it never silently fails.

**Key decisions locked with the user:**
| Decision | Choice |
|---|---|
| Purpose | Portfolio showcase + learning (Claude writes code + explains) |
| Build strategy | **Vertical slices** — always a runnable app; auth first, then one full role at a time |
| First slice | **Donor journey** (browse → donate → receipt → track) |
| Repo layout | **Monorepo** — shared Zod schemas/types across front & back |
| Services | **Hybrid** — real Postgres + real Cloudinary; email mocked initially. **Payments = real Stripe test mode** (upgraded from mocked per the requirement above) |

**Money never actually moves.** "Fund release" between funder→NGO is a status/ledger transition in our DB, not a real transfer. Donations run through Stripe **test mode** only. Claude never enters card details — the user types test cards into Stripe's own hosted checkout during testing.

## Architecture

**Monorepo (pnpm workspaces):**
```
ImpactBridge/
├─ apps/
│  ├─ web/          # React + Vite + TS + Tailwind + shadcn/ui + React Query + RHF + Zod + React Router
│  └─ api/          # Node + Express + TS + Prisma + Postgres + JWT + Zod + (later) Socket.io
├─ packages/
│  └─ shared/       # Zod schemas + inferred TS types shared by web & api (single source of truth)
├─ docker-compose.yml   # Postgres (+ Redis later)
├─ pnpm-workspace.yaml
└─ package.json         # root scripts
```

**Why this shape:** the `shared` package means a Zod schema (e.g. `donationCreateSchema`) is written once and used for API validation *and* front-end form validation *and* TS types — end-to-end type safety, which is exactly the "thoughtful" signal interviewers like.

**Core stack choices & rationale (explained as we build):**
- **Auth:** JWT **access token** (short-lived, in memory) + **refresh token** (httpOnly cookie); passwords hashed with **argon2**; email verification + forgot-password via signed tokens; **RBAC middleware** keyed off role. Google OAuth added after email/password works.
- **Validation:** Zod everywhere (shared package). Express error-handling middleware maps Zod/Prisma errors to clean JSON.
- **Data:** Prisma + Postgres. Migrations checked into git.
- **Frontend data:** React Query for server state; React Hook Form + Zod resolver for forms; route guards per role.

## Data Model (~15 tables)

Built incrementally per slice, but the target shape:

- **User** — email, passwordHash, name, emailVerified, role (enum: NGO_ADMIN | DONOR | FUNDER | PLATFORM_ADMIN), googleId?, avatarUrl
- **Organization** (NGO) — name, mission, category, location (lat/lng), verified, rating, fundingGoal, ownerUserId → User
- **Cause / Category** — category taxonomy (Education, Healthcare, Women Empowerment, Animals, Disaster Relief, Environment)
- **Donation** — donorUserId, organizationId, amount, currency, recurring, stripePaymentIntentId, status, receiptUrl
- **Transaction** — ledger row for every money-ish event (donation, fund allocation, release); type, amount, refs
- **Grant** — funderUserId, title, description, amount, eligibilityRules(JSON), category, deadline, status
- **GrantApplication** — grantId, organizationId, status (the workflow enum), submittedAt, answers(JSON)
- **Review** — grantApplicationId, reviewerUserId, score, decision, notes
- **Comment** — polymorphic-ish reviewer comments on applications
- **Project** — funded work an NGO runs (post-grant)
- **Report** — progress updates (photos, videos, expense reports, milestones) → Project
- **Document** — NGO legal docs (registration cert, PAN/GST, annual reports) → Organization; Cloudinary URLs
- **Notification** — userId, type, payload, read
- **Bookmark / Favorite** — donorUserId ↔ organizationId
- **Follow** — donorUserId ↔ organizationId
- **AuditLog** — actorUserId, action, target, metadata, timestamp

**Grant workflow state machine (GrantApplication.status):**
`DRAFT → SUBMITTED → REVIEW_PENDING → REVIEWER_ASSIGNED → INTERVIEW → APPROVED → FUNDS_RELEASED → IN_PROGRESS (reports) → COMPLETED` (+ `REJECTED` terminal). Transitions guarded server-side by role.

## Phased Roadmap (vertical slices)

### Phase 0 — Scaffold (runnable "hello world")
- Monorepo: pnpm workspaces, root scripts, TS config base, ESLint/Prettier.
- `apps/api`: Express + TS server, health route, env loading (zod-validated env), error middleware.
- `apps/web`: Vite + React + TS + Tailwind + shadcn/ui init, React Router shell, React Query provider.
- `packages/shared`: first shared Zod schema + build wiring.
- `docker-compose.yml`: Postgres; `.env.example`; Prisma init + first migration (empty/User stub).
- **Verify:** `docker compose up -d`, `pnpm dev` runs web + api; web hits api `/health` and shows OK.

### Phase 1 — Auth & Roles (foundation for every dashboard)
- Prisma **User** + role enum; migration + seed (a Platform Admin + a couple demo users).
- Register / login / logout; argon2 hashing; JWT access + refresh (httpOnly cookie); refresh endpoint.
- **Email verification** + **forgot/reset password** via signed tokens — *dev mailer logs the link to the console* (real Resend later).
- **RBAC middleware** + `requireRole(...)`; `/me` endpoint.
- Web: signup (role picker: NGO/Donor/Funder; Admin seeded), login, verify-email, forgot/reset pages; auth context + React Query; **route guards** redirecting by role; role-based dashboard shells (empty for now).
- **Verify:** register → see verification link in api logs → verify → login → land on correct role dashboard; protected route rejects wrong role.

### Phase 2 — Donor Journey ⭐ (donations MUST work — Stripe test mode)
- Prisma: **Organization**, **Category/Cause**, **Donation**, **Transaction**, **Bookmark**, **Follow**; seed ~6 demo NGOs across categories with images.
- **Browse & discover:** NGO list + card grid, **search** by name, **filters** (category, location, verified-only, funding goal, rating), NGO **public profile** page (impact metrics, causes, gallery).
- **Donations (real Stripe test mode):**
  - Server creates a **Stripe Checkout Session** (or PaymentIntent + Payment Element) for the chosen amount/NGO.
  - **Stripe webhook** endpoint verifies signature, on `checkout.session.completed`/`payment_intent.succeeded` writes **Donation + Transaction** and marks status paid. *This is the piece that failed last time — we build and test the webhook explicitly with the Stripe CLI so confirmation is reliable.*
  - **Receipt** generated (HTML → downloadable PDF) with a `receiptUrl`.
  - Optional **monthly recurring** via Stripe subscription (test mode) — after one-time works.
- **Donor dashboard:** total donated, donation history, download receipts, **favorites/bookmarks**, **follow NGOs**.
- **Verify (the headline demo):** log in as donor → open an NGO → donate with test card `4242 4242 4242 4242` → Stripe CLI forwards webhook → donation appears in history, receipt downloads, donor total updates. Also test decline card `4000...0002` shows a clean failure.

### Phase 3 — NGO Journey
- NGO dashboard: create/edit **own Organization** profile; **upload documents & images/videos via real Cloudinary** (registration cert, PAN/GST, annual reports, gallery); add **causes**, **team members**, **impact metrics**; view **donations received** for their org; view analytics.
- **Verify:** NGO edits profile, uploads a doc to Cloudinary (URL persists), donation from Phase 2 shows under "donations received".

### Phase 4 — Funder + Grant Workflow ⭐ (the standout)
- Prisma: **Grant**, **GrantApplication**, **Review**, **Comment**, **Project**, **Report**.
- Funder dashboard: **post grant** (+ eligibility rules), review applicant NGO profiles, **compare** applicants, **approve/reject**, **allocate funds** (ledger transition, not real money), reviewer **comments**.
- NGO side: **apply** for grants, **track application status** through the state machine.
- Post-approval: **Project** + **Report** progress updates (photos, videos, expense reports, milestones) so donors/funders see where funds go.
- **Verify:** funder posts grant → NGO applies → funder moves it through states to APPROVED → FUNDS_RELEASED → NGO posts a progress report; illegal transitions blocked by role/state guards.

### Phase 5 — Platform Admin
- Verify/suspend NGOs, manage users, moderate content, analytics dashboard, revenue/donation tracking, **audit logs** (write AuditLog on sensitive actions throughout).

### Phase 6 — Real-time Notifications
- **Socket.io** + **Redis** (add to docker-compose); Notification model already present. Events: grant approved, donation received, new grant posted, application submitted. In-app toast + notification center.

### Phase 7 — AI Layer (Claude API) — purposeful, not decorative
- Summarize NGO proposals; detect missing info in applications; draft grant applications; **match NGOs ↔ grants**; generate impact-report summaries from uploaded updates. Built over real data once it exists.

### Phase 8 — Analytics, Infra & Deploy
- Charts: monthly donations, top donors, funding distribution, grant utilization.
- Dockerize; **GitHub Actions** CI (typecheck, lint, test, prisma migrate); deploy **web → Vercel**, **api + Postgres + Redis → Railway/Render**.

- **Phase 2:** Stripe **test** keys (publishable + secret) and run the **Stripe CLI** for local webhook forwarding (Claude gives exact steps). No real card, no real money.

## Global verification approach
Each phase ends with a concrete runnable check (listed above). We keep `pnpm dev` green (web + api + Docker Postgres) at all times, add a minimal test as slices stabilize, and treat the **Phase 2 live donation demo** as the acceptance gate for "donations work."
